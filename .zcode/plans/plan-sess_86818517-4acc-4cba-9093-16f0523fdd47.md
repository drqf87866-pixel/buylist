# Umsetzungsplan: „buylist" – geteilte Einkaufsliste auf Cloudflare Workers

Grünfeld-Projekt (Ordner ist leer), Node v26.7.0 vorhanden. Umsetzung exakt nach deiner Spezifikation, in der vorgegebenen Feature-Reihenfolge. Eine getroffene Entscheidung vorab:

**Magic-Link-Login: nicht im MVP.** MailChannels' kostenlose Workers-Integration wurde 2024 eingestellt, Resend braucht Account + API-Key (externer Dienst, widerspricht „ein Deployment, keine externen Dienste"). Der Auth-Code wird so strukturiert, dass Magic-Link später sauber ergänzt werden kann (eigene Token-Tabelle-bereite Utility + Route-Platzhalter im README dokumentiert).

## Weitere Design-Entscheidungen (mit Begründung)

- **Passwort-Hashing: PBKDF2-SHA256 via `crypto.subtle`** (100.000 Iterationen, 16-Byte-Salt pro User, `timingSafeEqual`-Vergleich, Format `pbkdf2:<iter>:<salt-b64>:<hash-b64>`) statt bcryptjs – nativ, kein npm-Dependency, keine CPU-Fallen im Free-Tier.
- **Sessions in D1** (kein KV): ein Binding weniger, Lookups sind per Primary Key schnell genug. Nur der **SHA-256-Hash des Tokens** wird gespeichert. Cookie `bl_session`, `HttpOnly; Secure; SameSite=Lax; Path=/`, 30 Tage, sliding renewal (Verlängerung wenn < 15 Tage übrig).
- **DO-State als JSON unter einem Storage-Key** (`state.storage.put("list", …)` – bei SQLite-backed DOs ohnehin SQLite-persistiert). Listen sind klein; Full-State-Sync ist am robustesten.
- **Broadcast = vollständiger Listenstand** (`{type:"sync", list}`) nach jeder Änderung – kein Client-Side-Diffing, kein Drift.
- **UI-Sprache Deutsch**, SPA-Routing per `history.pushState` (passt zu `not_found_handling: "single-page-application"`).

## Konfiguration (wrangler.jsonc)

- `main: "src/index.ts"`, aktuelles `compatibility_date`, `name: "buylist"`

## D1-Schema (Migration 0001)

`users(id, email UNIQUE COLLATE NOCASE, password_hash, display_name, created_at)`,
`lists(id, name, owner_id, invite_token UNIQUE, created_at)`,
`list_memberships(list_id, user_id, role CHECK owner|member, joined_at, PK(list_id,user_id), Index auf user_id)`,
`sessions(token_hash PK, user_id, expires_at, created_at, Index auf user_id)`.

## Backend

**Router (`src/index.ts`):**匹配 `/api/*` → Auth-/Listen-Handler; unbekannte GET-Requests → `env.ASSETS.fetch(request)` (liefert SPA-Fallback). 404/405-Handling für REST.

**Auth (`auth.ts` + `session.ts`):**
- `POST /api/auth/register` – Validierung (E-Mail-Format, Passwort ≥ 8 Zeichen, Anzeigename ≥ 1), PBKDF2-Hash, User + Session anlegen, Cookie setzen. Duplicate-Mail → 409 mit klarer Meldung.
- `POST /api/auth/login` – Verify gegen Hash, Session ausstellen (32-Byte-Token base64url, nur Hash in D1).
- `POST /api/auth/logout` – Session löschen, Cookie löschen.
- `GET /api/auth/me` – Session-Check → User-Info (für SPA-Bootstrapping).

**Listen (`lists.ts`):**
- `GET /api/lists` – Listen des Users (JOIN memberships+lists+Owner-Name).
- `POST /api/lists {name}` – Transaktionsartig: D1-Rows (list, membership owner) anlegen, dann `stub.fetch(/init)` am DO (`idFromName(listId)`) mit Name.
- `GET /api/list/:id/snapshot` – Membership-Check → DO `/snapshot`.
- `GET /api/list/:id/ws` – Session + Membership-Check → Request an DO-Stub weiterreichen, User-Kontext serverseitig als Header `x-user-id`/`x-display-name` gesetzt (eingehende gleichnamige Header werden vorher entfernt, kein Spoofing).
- `POST /api/list/:id/join` – per Invite-Token (`POST /api/join {token}`): Membership anlegen (idempotent), Liste zurückgeben.
- `GET /api/list/:id/invite` – Invite-Link generieren/ausgeben (Owner+Member).

**ShoppingListDO (`do/shopping-list.ts`):**
- `fetch()`-Routen: `/init`, `/snapshot`, `/ws` (`ctx.state.acceptWebSocket(server)` + `serializeAttachment({userId, displayName})`), `setWebSocketAutoResponse("ping"→"pong")` für Heartbeats ohne Wake-up.
- `webSocketMessage`: `add` (uuid + timestamp serverseitig, `hinzugefuegtVon` = displayName aus Attachment), `toggle`, `delete` → State mutieren, `storage.put`, `sync` an alle via `ctx.getWebSockets()` broadcasten.
- `webSocketClose`/`webSocketError`: Server-Close. State bleibt in Storage (Feature 5 erfüllt).

**WS-Protokoll:** Client→DO: `{"type":"add","name","menge?"}` / `{"type":"toggle","itemId","erledigt"}` / `{"type":"delete","itemId"}` / `"ping"`. DO→Client: `{"type":"sync","list"}` nach jeder Änderung, `{"type":"error","message"}` bei ungültigen Messages.

## Frontend (Vanilla, kein Build-Step)

Views in einer SPA (`public/`):
- **`/login` & `/register`** – eine View mit Tab-Umschaltung, Fehlermeldungen inline.
- **`/` (Startseite)** – geschützt: Liste der eigenen Listen (Name, Member-Anzahl, Link), Button „Neue Liste" (Inline-Formular, großes Tap-Ziel), Bottom-Nav/Logout.
- **`/list/:id`** – geschützt: Snapshot laden, WS öffnen (Auto-Reconnect mit Backoff, Offline-Hinweis), Add-Bar unten (Name + optionale Menge), Checkbox groß zum Abhaken, Papierkorb zum Löschen, „Einladen"-Button (Invite-Link kopieren / `navigator.share`), erledigte Items optisch abgesetzt.
- **`/join/:token`** – eingeloggte User treten per Button bei; nicht eingeloggte werden nach Login zurück zur Join-Seite geleitet.
- Routing: `location.pathname`-basiert + `pushState`, Guard: ohne gültige Session (`/api/auth/me`) → Weiterleitung `/login`.

## Implementierungs-Reihenfolge

1. Grundgerüst: `package.json`, `tsconfig`, `wrangler.jsonc`, `.gitignore`, `npm install` (wrangler, typescript, @cloudflare/workers-types als devDependencies)
2. D1-Migration `0001_init.sql` + `wrangler d1 migrations apply buylist-db --local`
3. Utilities + Session-Layer (`util.ts`, `crypto.ts`, `session.ts`)
4. Auth-Routen → manuell gegen laufenden `wrangler dev` testen (curl + Cookie-Jar)
5. Listen-Routen + D1-Anbindung
6. `ShoppingListDO` (Hibernation, Storage, Broadcast) + WS-Upgrade & Snapshot
7. Frontend: Shell/Styles → Auth-Views → Listen-Übersicht → Listen-Detail mit WS
8. README (Setup, lokale Migrationen, Deployment: `d1 create` → database_id eintragen → `migrations apply --remote` → `deploy`)

## Verifikation (alles lokal mit `wrangler dev`)

1. `wrangler d1 migrations apply buylist-db --local`, dann `wrangler dev` im Hintergrund starten.
2. API-Tests per curl: Register → Login (Cookie) → `me` → Liste anlegen → Listen abrufen → Snapshot → Join via Invite-Token; Negativ-Tests: ohne Session 401, Nicht-Mitglied an fremder Liste 403.
3. Realtime-Test mit Node-Skript (v26 hat nativen WebSocket-Client): zwei WS-Clients auf dieselbe Liste, `add` in Client A → `sync` bei A und B asserten; DO-Neustart simulieren (State nach Reconnect erhalten).
4. Browser-Smoke-Test der UI (Registrierung, Liste anlegen, Item hinzufügen/abhaken/löschen, zweiter Tab = Live-Sync sichtbar).
5. `wrangler deploy`-Trockenprüfung der Konfiguration (`wrangler deploy --dry-run`), da kein Cloudflare-Login garantiert ist.
